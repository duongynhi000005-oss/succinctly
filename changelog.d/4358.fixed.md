- **jq: a number or keyword directly followed by another token byte is one malformed token, as in jq** (#4358). jq's lexer takes the whole run of bytes up to a boundary (whitespace and `"[{,:]}`) as one bare token, so `23null`, `1true`, `1e5true`, `-1null` and `0x` raise `Invalid numeric literal` and read nothing, where `succinctly jq -c .` read `23` and `null` (and `0` before failing on `x`). The document splitter ended a number at its last number byte and let the next token start there; a bare token whose next byte is not a boundary is now refused at its start. `23 null`, `2"a"`, `[1]2` and `"a"2` are unchanged (two values in both tools), and `12xyz`, which printed `12` before failing, now prints nothing as jq does. An old-versus-new differential against jq 1.7.1 over random multi-file splits with mismatched closers, adjacent tokens and invalid or truncated UTF-8 in the pool (2,400 runs) moved 268 runs to jq's answer and none the other way; the share still differing from jq fell from about 1 in 6 to about 1 in 40.
