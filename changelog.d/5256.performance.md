- **jq: a `reduce` whose assignment target needs the path-mode interpreter no longer copies its accumulator on every step** (#5256). `reduce .[] as $r ({}; getpath([$r.name]) = $r.score)` (and `|=`, `+=`, a conditional target `(if c then .[$r.name] else empty end) = ...`) went through `assign_native`/`modify_native`, which wrote each path while the path evaluator still held the document, so every step copied the whole container (quadratic in the number of steps; jq writes in place). The writes now wait for the paths to finish (at most 4,096 paths are held back; a longer run writes as it goes, as before), after which the accumulator is held alone and is written in place. An error the paths raise after an earlier path is raised after that path's write, so a write's own error still comes first, as in jq 1.7.1; a target whose paths have an effect of their own (`input`, `debug`, a `label`) is written as it goes, as before. Measured on an Apple M5 Max (release builds, 3 runs each, ~80 ms process-spawn floor included, output identical to jq 1.7.1): `getpath([$r.name]) =` 0.270 s → 0.087 s at 5,000 records, 0.925 s → 0.084 s at 10,000, 3.61 s → 0.080 s at 20,000 (jq: 0.08 s); `|=` 0.251 s → 0.080 s, 0.895 s → 0.088 s, 3.45 s → 0.088 s; `+=` 0.257 s → 0.079 s, 0.941 s → 0.083 s, 3.59 s → 0.086 s. A `label` in the target, or a variable that binds the accumulator (`. as $acc | ...`), still copies it on every step, as jq's own do; a `def` in the program is a different route (#5263).
