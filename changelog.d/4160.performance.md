- **jq: a run over a large document no longer counts newlines for a location nothing reads** (#4160). The default document loop resolved every value's `(at <file>:<line>)` line before evaluating, a scalar pass over the whole input, though only a diagnostic reads it and the M2 fast path never does; on the M2 fast path it is now resolved only if an error is reported, and every path counts in 64-byte chunks that vectorize. Two effects are in the numbers, so each row says which it exercised (interleaved A/B, output identical on every row). The chunked count alone, on **general-path** rows (`length` is not an M2 builtin per `can_use_m2_streaming`, and `[.[]?] | length` costs the same instructions with `--arg`, which disables M2, as without): `length` and `[.[]?] | length` -1.6% on a Ryzen 9 7950X and -1.9% on an M4 Pro (21 reps, every row faster; controls +0.03% / -0.61%). The lazy resolution on rows that really take M2, 21 reps: `.users[0]`, `.users[-1]` and `.users[]` on a 1.35 to 6.9 MB `users` document -2.5% / -3.2%, NDJSON `.name` -4.6% / -4.5% and NDJSON `-c .` -5.1% / -5.2% (7950X / M4 Pro; controls within +-1.4%). The identity fast path `-c .` on a single 2-10 MB document is -3.1% / -2.6% (15 reps; control +0.2% / -1.2%). For `.users[0]` the lazy route is under 1% of the instructions saved (0.7%) and the chunked count is the rest; on per-value NDJSON the lazy route is the larger share (about 6.1 M against 3.9 M instructions on a 2 MB file). Wall-clock did not separate the two effects. `find_matching_close`, the other term the issue names, is unchanged.
