- **jq: a run over a large document no longer counts newlines for a location nothing reads** (#4160). The default document loop resolved every value's `(at <file>:<line>)` line before evaluating, a scalar pass over the whole input, though only a diagnostic reads it and the M2 fast path never does; on the M2 fast path it is now resolved only if an error is reported, and every path counts in 64-byte chunks that vectorize. Two effects are in the numbers and the rows below say which one each exercised. Interleaved A/B, output identical on every row, same-binary control per family: the identity fast path `-c .` on 2-10 MB inputs is -3.1% (median of medians, 15 reps) on a Ryzen 9 7950X (-4.5% to -2.0% per row) and -2.6% on an M4 Pro (-3.9% to -1.7%), control +0.2% / -1.2%. `length` and `[.[]?] | length` are **general-path** rows, not M2 (`length` is not an M2 builtin, and `--arg`, which disables M2, costs the same instruction count to within 0.05%), so what they measure is the chunked newline count alone: -3.9% and -3.4% in the original 15-rep run, -1.6% (7950X) and -1.9% (M4 Pro) in a 21-rep re-measurement, every row faster. The lazy resolution itself shows on the routes that really take M2: `.users[0]`, `.users[-1]` and `.users[]` on a 1.35 to 6.9 MB `users` document -2.5% (7950X) / -3.2% (M4 Pro), and per-value NDJSON `.name` -4.6% / -4.5% and `-c .` -5.1% / -5.2% (controls within +-1.4%). On one large value most of that gain is the chunked count and the lazy route adds under 1% (`.users[0]`: 0.7% of instructions); on per-value NDJSON the lazy route is the larger share (about 6.1 M against 3.9 M instructions on a 2 MB file). The timed rows include both effects; wall-clock did not separate them. `find_matching_close`, the other term the issue names, is unchanged.
