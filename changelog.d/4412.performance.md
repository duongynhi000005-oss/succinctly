- **jq: `path(try .a)` and `path(try .a catch empty)` take the same cursor walk as `path(.a?)`** (#4412). `try E` and `try E catch empty` are `E?`, but the walk only recognised the `?` spelling, so a `try` fell to the route that copies the input and wraps the copy in an `Rc` on every `path(f)` call: two allocator calls per scalar member against one for `path(.[]?)`. The walk now takes both spellings in jq mode (a handler that runs, `catch .`, or a body that is not navigation keeps its route; yq mode keeps the materializing route, because the walk counts a repeated mapping key once more). `[.[] | path(try .a)] | length` over 1,000,000 integers took 140.2 ms on an Apple M4 Pro and now takes 95.7 ms (`path(.a?)`: 96.3 ms); on a Ryzen 9 7950X (one core) 192.6 ms to 130.1 ms (`path(.a?)`: 129.7 ms). `try .[0]` and `try .a catch empty` move the same -31% to -34%, `try .[]` -19% to -20% (it reaches `path(.[]?)`'s floor, 112.9 ms and 152.9 ms). Allocator calls for 2,000 members: `.[] | path(try .a)` 4,000 to 2,000. Release builds, interleaved min of 9, output identical on every row; `path(.a?)`, `path(.[]?)` and `path(first(.a?))` unchanged. `path(first(f))` keeps the materializing route: the walk collects every path before delivering one, which would make `path(first(.[]))` O(n) in memory.
