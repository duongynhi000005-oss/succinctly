- **jq: a value spanning two files is stitched under `input`/`inputs` when a file holds an invalid UTF-8 byte** (#4335). With `a.json` = `1<TAB>"\xff"  "a` and `b.json` = `b"<LF>`, `succinctly jq -nc '[limit(5; repeat(try input catch .))]'` read `[1,"\ufffd","Invalid JSON text","Invalid JSON text","break"]` where jq 1.7.1 reads `[1,"\ufffd","ab","break","break"]`, and the end-of-input marker lost its `<unknown>` the same way. The search for a file's open tail splits strictly under `input`/`inputs`, and the strict splitter judged the raw `\xff` inside a string a refusal, though jq substitutes U+FFFD for it before it reads the string. A span that only fails on an invalid byte is now judged after the same substitution. Recorded residual: a malformed value that also holds an invalid byte still resumes at the wrong read (#4349). A differential against jq 1.7.1 over random two- and three-file splits, none holding a parse error, with `"\xff"`, `"a\xe2\x82"`, `"\xe2\x82\xac"` and `"\xc3"` in the value pool had 16-17 differing runs per 250 streams before this and none after.
