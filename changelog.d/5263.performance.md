- **jq: `reduce .[] as $r ({}; .[$r.name] |= (. // 0) + 1)` and `reduce .[] as $r ([]; .[length] = $r.score)` are linear again** (#5263). A `reduce`/`foreach` assignment whose key, right side or update filter reads the accumulator (`(. // 0) + 1`, `if . == null then 1 else . + 1 end`, `length`, `.n`) declined the in-place write and copied the accumulator on every step, quadratic in the number of steps (jq writes in place). Such an operand, when it is a single-output expression with no effect, is now evaluated on the state before the write, so the fold hands the state to the write unshared. An operand that raises or yields nothing still takes the evaluator's route and text. Measured on an Apple M5 Max (release builds, interleaved, min of 3, ~80 ms process-spawn floor included, output identical to jq 1.7.1): the counting idiom `|= (. // 0) + 1` 0.88 s → 0.09 s at 5,000 records, 3.12 s → 0.08 s at 10,000, 12.75 s → 0.08 s at 20,000 (jq: 0.09 s); `.[length] = $r.score` 0.38 s → 0.08 s, 1.42 s → 0.09 s, 5.55 s → 0.08 s; `.[$r.name] = length` 1.25 s → 0.09 s, 4.87 s → 0.09 s, 19.9 s → 0.09 s (jq: 0.37 s at 20,000). A program that defines a function with `def` and calls it in the key still runs on the evaluator's copying route.
