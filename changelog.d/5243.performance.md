- **jq: `reduce .[] as $r ({}; .[$r.name] = $r.score)` is linear again** (#5243). Since #5223 a path target whose index key was anything but a bare variable (`.[$r.name]`, `.[.k]`, `.[$i + 1]`) counted as dynamic and ran on the path-mode interpreter, which copied the accumulator on every step. Such a key only computes a value (jq runs it as a subexpression), so the target is static and runs on the streaming walkers again, as before #5223. Measured on a Ryzen 9 7950X (release builds, interleaved, output identical to jq 1.7.1): 0.357 s → 0.009 s at 5,000 records, 1.417 s → 0.016 s at 10,000, 5.665 s → 0.031 s at 20,000 (jq: 0.03 s). A key that can retry a `?//`, calls a function, uses a label or an input builtin, or holds a dynamic path target of its own still runs on the interpreter; one that reads a succinctly extension (`.a[line | tostring]`) is still refused. Like every other `reduce` on the shipped evaluator, the idiom is bounded again by the documented 100,000-step `reduce`/`foreach` budget (#2079), which the interpreter does not have.
