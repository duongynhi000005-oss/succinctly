- **jq: a fault met inside the bytes moved onto a file resumes in the next read, and a bare token's run goes to the boundary** (#4376). Under `input`/`inputs`, a malformed value that began in one file and ended in the next (`[ "x<LF>y" ` then `"a\nb"<TAB>`, a string holding a raw newline, which jq meets at its closing quote in the first file's second read) was resumed from the next file's own first read, so that read, and the value in it, went missing; the error's `input_line_number` also counted from the wrong file. jq's read holding the fault is the previous file's: it ends at that file's next newline or at its end, and jq has counted that file's lines through it. The stitch now records how many newlines the previous file held ahead of the moved bytes, and a fault met in them resumes at the end of that read (not when the bytes came from more than one file). A bare token's run in fault placement also goes to the boundary whatever its bytes are (`\` belongs to the run), so a fault in `"a "\` followed by a space is met at the space, in the next file. An old-versus-new differential against jq 1.7.1 over random two- and three-file splits (mismatched closers, malformed containers, strings ending in a backslash, invalid or truncated UTF-8; two catching programs, one reporting `input_line_number`; 2,400 runs) moved 63 runs to jq's answer and none the other way.
